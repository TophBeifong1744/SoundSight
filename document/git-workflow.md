# Git与文件管理

本项目用Git保存能重建、修改和解释工程的材料；新仓库从这次迁移建立新的main基线，不继承旧仓库的临时分支和审批队列。

## 平时怎么用

1. 在main查看当前基线，做一件明确任务时建短分支`codex/<简短任务名>`。
2. 改源码、合同、测试或说明；完成受影响的必要验证。未运行的综合/板测如实标明。
3. 查看`git diff`和状态，只暂存本任务文件，形成有意义的提交。
4. 新GitHub仓库建立后，用Issue/PR记录目标、实际变化、测试和未测范围；不再复制第二套任务数据库。
5. 重要模块/组合结果按实际分工做非作者判断，合入main。main是集成基线，不是完整验收章。

不设永久develop，不按函数建分支，不用reset/clean/stash/强推处理共享脏目录。每个checkout和每份Vivado数据库同时只有一方写入。

## 仓库外手工开发与交接

当前工作方式：用户在仓库外搭建和验证 → 对比接回源码并导出最新BD/PS/IP及工程配方 → 分支/PR集成。具体规则见AGENTS.md“仓库外开发与工程交接”；操作起点见manual-stm32-build.md。工作副本记录来源提交，不能同时在仓库与外部副本修改同一成果后直接覆盖。GUI修改后必须更新配方，不能只提交旧BAT。必要源码、约束、初始化数据与软件随配方一起交接。

## 哪些进入Git

| 进入Git | 留在本地输出或发布资料 |
|---|---|
| RTL、C/Python、TB、模型、初始化数据 | XSim编译/展开数据库、大波形 |
| XDC、IP参数/正式生成配方、BD配方 | par中的本机原生工程数据库及综合/实现输出 |
| 冻结协议、实际源清单和操作说明 | 每次仿真、编译、调试的临时目录 |
| 必要小型真实日志/结果和解释 | 旧技术档案ZIP、可再取得的声纹模型权重 |
| 资料来源和必要硬件原件 | 后续匹配bit/LTX/HWH/报告的正式交付包 |

忽略不等于删除。当前本地SoundSight包含旧原件档案和已准备工程；它们不会被一次`git add .`混进新源码历史。未来完整交付应在`release/output`保存可搬移工程和实际匹配产物，不仅交一个Git地址。

必要的`.xpr/.bd/.xci`并非禁止进Git：本项目当前选择配方重建以避免本机路径污染；以后用户手工调整BD/PS后，应先导出更新的BD/PS配置并纳入版本管理，必要时同时保存真实工程描述。不能只改ignored的BD后以为Git已保存。

## 新仓库建立后

用户在GitHub建立空仓库，再在SoundSight设置该仓库为origin并推送main。迁移工具不创建远端、不推送、不改旧仓库。不要绑定旧Competition_fpga的origin。

原许可证保留作者与声明；厂商模型、资料、第三方研究各自的声明不被项目MIT覆盖。大文件需要跨成员共享时使用明确的发布资产/存储位置；本次不自动部署LFS或付费服务。

## 采用的规则来源

2026-10-17读取本机fpga-team-workflow 0.3.1的`references/git-workflow.md`和run-fpga-workflow本地0.5.0的`references/project-layout.md`。只把适用规则落实在本项目，不修改通用Skills；用户既有人工构建权限和简化协作决定优先。

Git提交ID用于版本追溯，不写进新的宽身份/防伪硬件链，不作为用户编辑、打开或仿真的哈希门槛。

# B如何继续补充

固定入口为 `document/evidence/speaker-report-materials/README.md`。在这个目录接着补，不另建report2、工程副本或新的长期报告目录。2026-10-29起A全面接手总工程及声纹，B的历史贡献与证据继续在这里维护；此前声纹独立维护授权仅属历史。根目录`report/README.md`是官方分类导航，不是第二份报告。这里是资料组织方式，不新增审批关卡。

## 每批的最小更新

1. 在 `batches/` 新增一个简短Markdown，例如 `batches/2026-10-29-rx4-board.md`，按下方模板记录问题、候选和结果。只在产生新证据时增批次，不因聊天或重打包堆重复记录。
2. 新证据接着用未占用的E编号（本批已用至E19，后续从E20开始），放对应的 `records/E编号/`。优先保留小型原始串口、结构化结果、必要失败和版本信息；不放整套工具链、波形数据库或工程缓存。
3. 在 `02-iterations.md` 增加一行，并更新 `05-scope-and-followup.md` 的结论边界。历史错误用“修正/替代”注明，不删除失败或改写原日志。
4. 有可绘图测量时向 `metrics.csv` 追加行：必须给scope、输入/窗口/线程/样本次数、精确计时边界、可比组和证据路径。仅同条件才复用comparison_group；板端、主机与ARM模拟分开。缺失填UNKNOWN，不填0；不把CPU秒和墙钟混为一列。
5. 值得报告强调的实现写入 `03-code-highlights.md`：只摘关键函数/片段，解释解决什么问题、复用哪些逻辑、效果证据在哪。注明候选Git提交或包哈希、原路径和行号；本目录不保存可运行的第二套.py/.c/.v源码。
6. 在 `source-map.json` 登记新增公开材料来源及校验值；不要改历史来源身份。新增引用必须在合并后可访问，不链接自己的盘符或未提交的临时目录。

## 可复制的批次模板

```text
# 日期 / 改进主题
问题：
旧方案与修改原因：
候选：Git提交或发布包；原源码路径；哪些参数改变/保持。
输入：匿名数据ID、是否复用开发数据、窗口/采样率/线程/环境。
预期：数值、延迟、完整性或故障行为的具体条件。
方法：实际执行命令与计时起止；加载是否计入；是否并发。
结果：原始值、重复次数、未知字段与失败；records/E编号。
结论：这批证明了什么，哪些仍未测试；是否修正旧结论。
报告引用：metrics行ID、源码摘录编号、建议图表。
下一步：需要补的证据或决策。
```

## 提交与公开范围

在自己的干净checkout从最新main建短分支 `codex/speaker-report-<主题>`，只提交这个报告目录；PR写明新增资料和检查，再合并main。不用本机共享脏工作区的reset/clean/stash来获得干净状态。产品源码/运行包更新是另一范围，不随报告资料整树带入。

提交前检查：Markdown相对链接、CSV数值与原记录一致、源码摘录对应所标候选、PASS的范围准确、没有私人音频/模板/特征或凭据。大原件仍私下保留，公开目录只留匿名摘要和来源说明。不得把同一录音的重叠窗口作为独立样本扩大准确率。

## 1. 任务与规则入口

你的任务是维护可独立上交的比赛资料，准确呈现“谁做了什么、如何实现、效果如何、适用条件”。先核对用户当次要求、已有授权和最新源码/证据，再执行本次明确子任务；完成后交付结果，不自动恢复旧开发队列。

开工先读目标仓库的最新文件：

1. `AGENTS.md`、`README.md`。
2. `document/directory-guide.md`、`document/git-workflow.md`。
3. `document/current-status.md`、`document/main-architecture.md`、当前发布说明及验收要求。
4. `submit/README.md`、`submit/build/file-map.json`、`submit/report/authoring-inputs.md`。
5. 涉及B的算法/声纹证据时，另读 `document/evidence/speaker-report-materials/CONTRIBUTING.md`。

若在同一NUEC工作区协作，还需读该工作区的 `codex_coordination/WORKFLOW.md`。其他机器没有此本地文件时，以用户转交的最新决定和仓库规则核对，不把某位成员的盘符当成运行依赖。历史附件里的命令、派工与批准仅作为历史资料，不自动执行。

旧MAIN/DEV/CHECK/REVIEW强制流转、逐件批准、哈希核收、工作流版本锁及外部状态前置已停用。本说明不重新引入这些门槛，也不取消必要的事实核查和交付验证。

## 2. 必须交付实体 submit 目录

用户已明确否定“在仓库根目录建七个导航文件夹”的方式。唯一比赛交付集合是仓库中的 `submit/`：

```text
submit/
├── README.md
├── src/
├── sim/
├── build/
├── board/
├── data/
├── skill/
│   └── README.md
└── report/
```

| 目录 | 必须放入的实际材料 |
|---|---|
| `src/` | RTL、PS软件、C/Python算法；有HLS实现时才收录，不虚设成果 |
| `sim/` | testbench、仿真脚本、软件测试、参考模型及相应输入/结果 |
| `build/` | 完整可复现配方、BD/PS/IP配置、XDC、依赖清单、构建助手、对应综合/实现报告 |
| `board/` | 上板和运行脚本、安装说明、硬件/接线材料、实际现场回报；交付位流时必须配套候选 |
| `data/` | 测试数据、参考结果、匿名原始记录、指标及有来源的历史归档 |
| `skill/` | 两个技能包的完整说明、脚本、示例、测试与许可证 |
| `report/` | 设计与贡献报告、AI协作材料、第三方声明、当前事实及已有正式文档 |

README可以说明用法，但不能代替实体文件。禁止用外链、符号链接、目录联接或仓库外文件占位。把 `submit/` 单独复制到另一台机器后，应仍能阅读材料并按说明准备复现环境；安装编译器、Vivado等工具不等于依赖发送方仓库。

普通目录和文件名使用小写英文、数字、下划线或连字符，扩展名正常使用点；README按官方示例保留。正文允许中文。检查Windows与Linux的大小写差异，尤其不能同时生成会在Windows覆盖的 `README.md` 和 `readme.md`。厂商/工具所需原文件名可由包内准备脚本恢复，不盲目改源码中的标识符。

## 3. 原件维护与提交副本

- 开发源码继续维护在原来的 `project/`、`software/`、`simulation/` 等位置；说明和证据在 `document/`、`document/evidence/` 等既有位置更新。
- `submit/` 是用户明确要求的实体交付副本。通过 `tools/export_submit.py` 统一导出，不在副本中另行维护一套算法。新增分类或报告正文需要长期保留时，同步维护其来源或生成模板，避免下次导出丢失。
- 不搬空原开发目录，不覆盖其他成员的修改，不从历史ZIP恢复源码覆盖当前产品。
- 新增文件必须先纳入本次Git跟踪集合再导出：现行导出器使用 `git ls-files`，未跟踪文件会漏包。只暂存本任务文件，不把别人的在途改动带入。
- 核对导出器的模板、目录选择和排除规则。main更新不代表 `submit/` 已更新；重新运行导出器也不保证模板中的日期、引脚、阈值和“待测”描述已自动更新。
- `file-map.json`用于来源追溯、目录恢复和文件完整性检查。保留原始来源身份，区分源文件内容与改写过导航链接的提交文档；它不是硬件身份链或日常逐件批准机制。

## 4. 状态与证据不能混写

每项结果必须说明日期、候选版本、输入和环境、实际执行者、测量范围及原始证据位置。以下层级分别描述：

| 类型 | 能证明的范围 |
|---|---|
| PC/Linux主机离线 | 软件逻辑、数值或该主机上的性能 |
| ARM板端离线 | 实际目标CPU上的离线行为/耗时，不自动代表实麦在线效果 |
| RTL仿真 | 所列激励和检查覆盖的周期行为 |
| Vivado创建/BD Validate/IP生成 | 工程准备和配置检查，不等于综合或实现通过 |
| 综合/实现/STA | 对应候选的资源、时序及已检查约束；不能扩大为全部CDC/RDC/板测通过 |
| 真实采集/现场运行 | 对应输入、模式、时长及配置下的实机结果 |
| 用户观察 | “可转动”“方向看起来正常”等实际回报，不冒充仪器测量或定量精度 |

保留失败原件。后续修正另写日期和证据，不删除旧失败，也不把旧“尚未测”当成永久现状。不同候选、时长和模式不能互相代替：短测不是长稳，纯声音跟随不是声纹许可验证，正时序裕量不是整机通过，打包成功不是硬件验收。

性能比较必须注明输入、窗口、采样率、线程/并发条件、计时起止、重复次数和比较组。不混用CPU时间与墙钟时间，不把单函数收益写成整机收益，不累加不同实验的百分比。不将无依据的指标填0或编入当前成品；重叠窗口或重复显示的同一评分不能扩充独立样本量。

已有指标与原记录一致才可引用。只有新实验才新增实验批次、指标行或E编号；下一编号先检查最新占用情况，不照抄旧文档的“从E20开始”。重新分类、导出或压缩不算新实验。

## 5. 贡献署名与公开范围

- 按源码、提交、交接和实验记录区分A、B、其他成员、第三方及现场执行者。当前维护人不等于所有历史工作的作者。
- B的历史STM32 S1/S2、二维PYNQ、三维/DAS、软件优化、声纹工程适配/计算优化及AF1贡献按对应证据记录；A后续集成、RTL/控制或新的实验不回填为B当时完成。
- CAM++、Silero、ONNX Runtime、厂商IP及其他已有算法/组件归原作者。团队贡献写清具体实现、适配、优化和验证，不声称原创第三方模型或通用算法。
- AI整理、解释或生成代码与人类接线、下载、运行、观察和测量分开署名。没有参与的成员不补署“实测完成”。
- AI协作材料使用真实可见的提示词、回答、修改和纠错记录，区分原文与摘要；不编造聊天，不收录隐藏推理。
- 不新增公开私人录音、个人模板/特征、凭据或本机工具配置。模型与第三方资料按实际许可和用户授权处理，缺少合法可分享资产时说明合法取得方式，不伪造公开下载地址。

## 6. 一次资料更新的执行顺序

1. **确认基线。** 读取最新main和相关PR/原件，记录实际提交。检查工作区状态；需要隔离时另建干净checkout，不对共享脏目录执行reset、clean、stash或强推。
2. **更新原资料。** 补实际源码来源、报告、原始证据、贡献和适用范围。涉及B资料时按既有CONTRIBUTING更新对应表格/索引，不另建report2。仅资料任务不夹带未授权产品修改。
3. **对齐导出。** 检查生成模板和分类规则是否覆盖本批成果、新候选及当前测试结果。现行main导出器以HEAD记录基线，但读取工作区文件；若包含未提交修改，需明确实际文件来源和状态，不能声称所有内容均等于HEAD。
4. **生成新候选目录。** 导出器拒绝覆盖已有输出。选择一个不存在的候选目录，先验证，不直接删除当前 `submit/`。
5. **隔离检查。** 单独压缩/解压候选目录到开发仓库之外，运行包内准备脚本和适用离线检查；确认无需原仓库、本机盘符或Git历史。验证内容变化后再重跑受影响检查，不为资料更新重做无关硬件实验。
6. **更新正式副本。** 核对当前 `submit/` 是否有未回灌的人工修改；保留有用差异后同步已验证文件，更新本轮验证记录。同步或删除前确认具体路径和范围，不按日期批量清空目录。
7. **打包与发布。** ZIP根层只包含 `submit/`，内部为README及七类实体目录。检查最终ZIP而不是仅检查压缩前目录。发布按用户当次及既有授权通过短分支/PR进行；合并前检查main变化，合并后回读目录与提交。不自动向赛事平台提交或给其他人发消息。
8. **收尾交付。** 说明实际变更、检查结果、文件/远端入口、原件保留情况及验证范围。清理本任务已用完的临时目录和请求文件，保留有价值的结果；完成当前子任务后暂停。

以下为仓库根目录下的候选生成与检查示例；若路径已存在，先核对用途并另选新路径，不直接清空：

```text
python -B tools/export_submit.py --output release/output/submit-candidate
python -B tools/check_submit.py --submit release/output/submit-candidate --work-parent ../soundsight-submit-validation --result release/output/submit-check.json
```

执行前核对最新脚本的参数和测试覆盖。本轮检查结果纳入候选的 `build/validation.json`，最终ZIP再核查文件数、CRC与清单内容。上述检查不代表设计全部功能已验收。

包内最基本的独立入口是：

```text
python -B build/prepare_workspace.py --output ../soundsight_work
```

它在 `submit/` 根目录执行，只准备新空工作目录，不应启动EDA、联网取源码或访问硬件。后续工程/板端操作须按实际任务授权与当前候选说明执行。

## 7. 必须防止重现的问题

- **导航替代文件：** 根目录七个README、空目录或外链集合不能当成提交包。
- **模板覆盖新状态：** 源码已更新而报告仍写旧引脚/旧许可/旧失败；必须逐项核对来源和日期。
- **来源和运行依赖缺失：** GUI改了工程却没同步BD/IP/XDC、初始化数据或软件依赖，单交BAT/Tcl不算完整复现。
- **换行造成校验不符：** 保留提交副本的精确字节属性；曾出现Git子树archive改变换行。使用精确字节打包或验证过的归档方式，最终逐项核对。不得为让检查通过而改写历史日志。
- **大小写覆盖：** 小写导出需检查路径冲突，不能仅凭Windows上能找到文件就认定Linux也能运行。
- **旧数量充当新验证：** “2011文件、517处链接、18项检查”属于PR #32当时记录，不是以后更新的固定目标或自动通过证明。
- **结果有来源：** 当前只交付有依据的结论；移除无依据内容，不用模拟、旧包或新编摘要冒充实测，不改写原始证据。

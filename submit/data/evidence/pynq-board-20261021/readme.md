## 失败原因，用大白话解释

FPGA持续产出结果，但公共接口只有两个缓存位置。旧软件每拿一帧，必须等SD卡确认写完才腾出位置。C计算通常只用约0.24ms；SD有时要十几到二十几毫秒。在约10.667ms一帧的预期工作节奏下，保存稍慢，后面的帧就会堆起来。满了以后硬件按原规则记录丢帧，软件发现故障后停止。

这与“音乐方向算错”不是同一个问题。新的RAM队列用于隔开短期写盘抖动；长期平均写速仍不够时必须停新增采集，不能无限积压。

| 尝试 | 失败/成功事实 | 恢复事实 |
|---|---|---|
| real-100-001 | consumed=5；序号10已写日志但未消费；FAULT=0x48，DROPS=1 | 排出10、11；10内容与原记录相同，属于重复保全 |
| SD同步诊断 | 100次1536B写入+fsync：min3.979、median4.650、p959.952、max21.405ms；4次超过10.667ms | 诊断不是实时程序实测吞吐保证 |
| real-profile-001 | 20帧完成；启动记录fsync13.625ms，采集记录中最大17.880ms | 尾帧33已保存，fault=0x40，drops仍1 |
| real-profile-002 | 请求100，consumed=3；34..37有保存记录；FAULT=0x48，DROPS=2，锁帧37 | 37、38已保存并消费，恢复日志saved=2；37重复，不能算新增采样 |

第二轮fsync顺序为 `[29.630,9.801,9.027,8.895,14.065,18.708] ms`，对应“启动、34、35、36、37、失败日志”。启动29.630发生在启动采集前，失败日志18.708在故障后，不能拿这两个数冒充直接触发溢出的帧时延。

序号37的取帧约1.087ms、求解0.247ms，再加fsync14.065ms，三者就约15.399ms，还没加进程通信。说明逐帧同步已明显占用服务余量；不是仅凭一条max统计猜测。精确的溢出时钟点未由ILA捕获，不能从软件日志反推出硬件逐周期因果。

0x48含溢出0x08与STOP/取消0x40；DROPS为累计值，本次从1增到2，新增一次丢帧。恢复成功说明已有37、38帧保住了，**不表示被丢弃的新帧找回了**。尾日志中frame.fault是读取时的全局故障快照，不代表C又重新算坏了该帧。

本轮结论：RAM缓冲后的100帧无动作采集、求解与保存试验按请求结束，报告零丢帧，支持对旧逐帧fsync阻塞问题的修复有效。默认高水位48条未触发；不能据此证明高水位实板路径、长时间零丢帧、机械闭环或角度精度。旧版100帧失败及恢复原文继续保留，供比赛展示问题定位与修复前后对照。

### 方向拒绝的配对层检查

后续用户回传保存在`ram-real-100-001-pairs-uart.txt`，按冻结头解码的两条样本见`ram-real-100-001-pair-decode.json`。全文件统计：有效方向中6/5/4/3组合格分别39/9/2/3帧；残差拒绝中5/6组合格分别5/12帧；30帧reason=1全部是0组合格，并非只有一两组不足。

样本序号56的六个FEATURE字为0x62000000至0x62000500：mask_count均0，PHAT阶段REJECTED(2)，IFFT阶段SKIPPED(6)，原始峰有效位和IFFT合格位均未置；各组四个相关峰值数据均0，故障/丢帧仍0。按当前仓库`ss_pair_engine.sv`，不足12个筛选频点会在PHAT_FINAL拒绝并跳过IFFT。这不是CPU收到六个合法零时差，也不是丢帧后补了六组零。

当前RTL筛选条件为频带7..85内互谱平方幅度非零且`2500*本频点平方幅度 >= 本对最大平方幅度`。若读写及状态推进符合实现预期，有非零互谱时至少最大频点应通过，因此mask_count=0值得继续核查全零/量化后归零频谱或数据路径；不能直接归结为“12这个门限太高”，也不能只凭输出断定物理声音静音。

后续统计原文见`ram-real-100-001-zero-mask-uart.txt`：30帧全部六对mask=0，序号为56、58、61..67、70、72..86、93..96、99。集中在后半段，夹杂恢复，并非整个后半段持续失效。用户随后在本聊天问答中确认测试期间有“暂停、切歌或调整音量”。因此原100帧试验存在声源变化，53%不能当作持续稳定声源下的有效率，更不能据此直接认定硬件故障。该变化可能解释部分拒绝，但缺少声源操作与帧时间对齐，不能认定30帧全部对应静音。下一步固定声源位置与音量、连续播放后做100帧对照；暂不改RTL、算法门限或系统swap配置。

样本序号6的六对PHAT/IFFT阶段均OK，mask_count为54/54/48/63/58/59；CPU筛选后5组合格，再以残差超限拒绝方向。这与56帧的PHAT阶段拒绝不同。声源频谱、音乐间隙、反射、几何/通道匹配或实现问题的具体归因仍未确定。

## 3. 四份成品统一采用的最终系统范围

以最终完整产品为叙述对象，功能范围已经确认，共四项：

1. **RGB触摸屏独立操作**：通过与开发板相连的FPC软排线接入显示和触摸，日常模式选择、参数配置、状态查看等不依赖电脑串口。
2. **三维声音定位**。
3. **声纹识别／说话人验证**。
4. **水平、垂直双轴指向**：手动标定、纯声音跟随和声纹许可跟随。

项目主方案为Zynq-7020 PL＋PS/PYNQ，不恢复STM32路线，不自行扩展六麦、云服务等为本次必须实现的主功能。扩大应用价值讨论，不等于扩大工程交付范围。

四项功能的具体接合关系以[当前组合](../final-function-scope.md)和实际证据为准。声纹从连续PCM获取语音并提供许可，不直接改变三维求解结果；延迟声纹许可不能描述为已完成多人声源身份与空间方向的严格绑定。触屏现有控制范围与终端录入入口分别写清。

## 4. 拓芙的个人写作要求

### 4.1 应用价值：充分展开完整产品的潜力

应用价值不局限于仓库目前实现到哪一步。以功能、可靠性、成本、部署和使用条件都充分成熟为前提，讨论完整系统能够解决多大的问题、服务哪些群体、进入哪些场景、如何推广及形成价值。

写作应建立明确的论证链：

**使用者与场景 → 实际痛点 → 系统提供的能力 → 用户收益 → 推广条件与规模潜力。**

可以合理展望更大的应用范围，不只停留在“板子能定位、舵机能转动”。但要说明关键成立条件，将潜在价值与已验证成效区分开，不把市场规模、成本下降或用户收益的假设直接写成实测或既成事实。

### 4.2 创新性：已有贡献加合理构想

创新点不局限于当前代码中已经完全实现的功能。允许基于现有方案提炼更完整的设计理念、提出技术上说得通的新机制或扩展设计。

每个创新点尽量回答：

- 针对什么问题或现有不足？
- 具体提出了什么机制、组织方式或设计？
- 为什么预期有效，实现路径是什么？
- 已有何种证据，哪些收益仍待验证？

已有成果用实测和实现支撑；尚未落地的合理创新可以作为提出的设计和预期机制进行论证，不必因尚未完成实现而完全不讨论。不能把简单功能组合换个名称就称为原创算法，也不把第三方模型、厂商IP或他人原模块归为本队原创。

应用价值侧重充分条件下的远景，创新性侧重具有技术依据的贡献与构想，两者不采用同一种夸大表述。

### 4.3 语言：正式、专业、偏论文式

两份报告采用正式、偏论文的表达，适当使用准确的专业术语，避免口语化开发流水账。术语要有对应原理、定义和机制，不能只追求听起来复杂。

可参考的表达方向：

| 口语描述 | 专业表达方向 |
|---|---|
| 声音太小就不给角度或动作 | 基于音量门限的方向输出与运动触发抑制 |
| 多帧角度筛选后一起计算 | 多帧方向估计融合与时域稳定化 |
| 声纹通过后保持一段时间许可 | 基于说话人验证的时限授权跟随机制 |
| 写卡慢不能堵住采集 | 采集与持久化解耦及有界缓冲机制 |

上表是措辞方向，不是预先认定的创新点。尤其不能将当前PCM幅度统计直接称为经过标定的声压级或声强测量。中英文术语、符号、单位在四份材料中统一。

## 5. 预写方式与独立核验清单

### 5.1 先写通，不等待所有证据齐备

报告可以先按最终成品状态组织成完整内部稿。正文不在每个段落反复插入“尚未印证”，避免写作被零散缺件打断；**整份文档统一保留内部预写稿标识，直到事实核验完成。**

遇到原计划按完成态写入、但尚未拿到证据的内容，单独登记到核验清单，并提醒拓芙向相应成员索取具体材料。若暂时拿不到，不阻塞其他章节，先完成设计说明、推理、预期效果和待补图表结构。

具体测量数字留空；确需示意数据时明确作为示例，不能伪装成实测。不编造实验、模型回答、协作经历、仪器截图或第三方结果作为真实事实。

### 5.2 核验清单要能定位和替换

建议字段：

| 字段 | 用途 |
|---|---|
| 条目编号 | 稳定追踪，同一事实跨材料共用编号 |
| 涉及材料与位置 | 技术报告／设计报告章节、海报区域、图表号 |
| 提前写入的表述 | 准确记录暂定的完成态结论 |
| 当前依据与真实状态 | 已有设计、已有实现、成员口头回报、待实测等 |
| 需要取得的材料 | 日志、测量表、截图、实物照片、视频或配置 |
| 索取对象／待明确对象 | 由实际职责确定，不凭空指定成员已承诺交付 |
| 暂定假设或留空项 | 后续需要替换的数值、效果和推理条件 |
| 核实结果与修改记录 | 收到什么证据，怎样修订各处结论 |

拿到真实结果后，不只是填数字，要同步修改正文、表格、图注、摘要和两张海报。如果结果不支持原预期，结论随之调整。

**正式提交前处理全部待确认项。** 不能因为内部清单记录了问题，就把未经支持的“已经完成／已经验证”保留在最终提交版；未完成部分应调整为方案、预期或实际状态。内部清单不能替代事实验证。

### 5.3 已明确的三项重点核验

| 编号 | 内容 | 需要补齐的依据 |
|---|---|---|
| V01 | RGB触摸屏实际操作 | 显示、触摸、模式切换与参数配置可用，脱离串口操作的现场记录和界面图 |
| V02 | 不同人的声纹对照 | 目标本人／其他人的分数与测试条件，门限依据、通过和误通过情况 |
| V03 | 三维方向与双轴实际指向 | 已知目标方位与俯仰、阵列及转台标定、实际指向和误差／响应记录 |

这些是当前重点，不是完整验收结论。四项功能的联合负载、停止保护和复现依赖仍按实际证据核对，不因未列入这三项就默认通过。

## 7. 设计报告的执行要求

### 7.1 没有固定模板时的处理

目前只有内容要求和评分表，没有提供固定设计报告模板。自主采用正式论文式结构，统一标题层级、图表编号、公式、术语与引用；不自行杜撰官方字数或页数限制。后续如收到老师的新模板，再映射章节和调整版式。

建议结构作为写作起点，不是已经冻结的赛方目录：

1. 摘要及项目概述。
2. 应用背景、需求与价值。
3. 创新构思与设计贡献。
4. 系统原理、功能框图、软硬件划分与接口。
5. 优化过程及性能、资源对比。
6. 功能验证与结果分析。
7. 大模型协作过程。
8. 技能包提炼、验证及适用边界。
9. 从零复现说明。
10. 总结、展望与参考文献。

设计报告重点回答“为什么这样设计、贡献在哪里、如何优化、证据是什么”，不能成为技术报告的重复版本。

### 7.2 七项内容全部覆盖

## 8. 优化过程的具体写法与证据

采用“**问题 → 原因 → 修改 → 验证 → 收益与代价**”的结构，选择关键版本，不写每日修改流水账。

### 8.1 可写的三条主线

**连续运行与存储调度**：逐帧等待SD写盘导致背压；内存队列解耦；正常运行与调试记录分开；最新定位结果策略。解释适用目标和代价，不把主动淘汰旧结果称为无损优化。

**PL控制与时序结构**：计算、故障判断、停止反馈形成长组合路径；通过分拍、寄存器隔离及重复依赖简化处理。选有准确候选和原始报告的节点，核对数值、服务预算及停止行为。当前仓库保留多批报告，但不能声称每一个早期版本都已有完整、可比的前后数据。

**声纹计算与采集协同**：结合现有基准测量，说明处理耗时、重复计算、调度与任务积压等优化。许可有效期调整只是跟随策略，**不等于推理速度提升**；离线固定输入测试不等于在线端到端性能。

### 8.2 对比表需要注明什么

版本／候选、平台、输入、运行条件、计时范围、性能指标、资源指标、正确性检查、代价及来源。尤其核对时钟、约束和硬件范围是否相同。

已有真实板端采集日志、千帧原件、声纹基准记录和实现报告，可以开始写作；但不能把不同输入或不同架构下的数字直接拼成提升倍数。没有的指标列入核验清单，不填假实测。

## 9. 大模型协作与技能包：已有明确写作素材

### 9.1 大模型协作

选择两三个典型案例，串起用户约束、AI建议／代码、实际报错、人工判断、修正和复测。可选方向包括采集写盘故障、工程导出与路径问题、模块验证判据的修正等，以实际原件完整程度决定。

用真实提示词与可见模型回答；仅有摘要时写成过程概述，不伪造聊天原文，不编写隐藏思维过程。讲清人如何约束、判断和纠正模型，也讲清测试怎样否定错误建议。不编造“AI节省百分之多少时间”等没有测量依据的结论。

### 9.2 两个已存在的比赛技能包

| 技能包 | 实际提炼的内容 | 已有验证及限制 |
|---|---|---|
| FPGA模块开发与仿真验证 | 从接口约定生成／组织RTL、自检TB和可复现验证；除数值外检查握手、逐拍延迟、容量和复位行为 | 有真实XSim；数据翻转、拒绝空槽输入、额外流水级等负例可检出。不代表整机、时序、CDC或板测通过 |
| PYNQ Overlay与DMA验证 | 配置和真实实例检查、数据比较、缓冲区所有权、超时与释放的生命周期验证 | 已有离线测试和模拟后端；真实PYNQ驱动适配器及该技能的实板验证仍待完成 |

可用的提炼叙述包括：“只比较输出数值会漏掉额外流水级”促成逐拍延迟／容量检查；DMA异常结束时不能贸然释放缓冲区，促成明确的状态和所有权处理。需要把历史发现、提炼实现和后续迁移复测分开，不把迁移时重新运行测试写成首次发现所有问题。

正式技能源码在`research/competition-skills/`。通用开发工作流工具不是本队原创技能成果。技能与生产程序的验证边界分别记录，不能以生产系统已经运行倒推技能适配器已完成。

## 10. 两份报告的图件要求

### 10.1 谁来提供什么图

- 原理图、综合电路图、实际实现结果、工具生成的复杂工程图：优先由能够操作原程序的人从对应软件导出，我负责说明所需内容、接收核对、裁剪及排版。
- 分析图、性能／资源对比图、曲线图、分布图等：由我依据数据生成。
- 实物照片、真实界面和测量截图需要实际来源，不能用重画或生成的示意图冒充。
- 为解释设计绘制的框图或流程图可以自行制作，但要与实际设计对应，并与工具原始导出图区分。

### 10.2 配色只限定两份报告

**以黑白为基调，不是全部只能黑白。** 背景、文字、坐标轴、边框以黑白和中性灰为主；不同曲线、类别和对比对象可使用少量清楚的颜色区分。同一对象跨图保持同色，必要时辅以线型、点型和纹理。

原始工程导出图不强制转灰度。保留原件；需要裁剪、缩放或转换时另存展示副本，不损失关键标注和证据信息。

### 10.3 必须检查的排版问题

- 文字不能超出所在框、单元格或图形边界。
- 标题、图例、轴标签、标注和数据点不能相互遮挡。
- 不能在页面边缘或导出时被裁切。
- 按报告中实际放置尺寸检查可读性，不能只看放大后的绘图窗口。
- 图号、表号、单位、说明与正文引用一致。

最终报告需渲染后逐页检查，不能只依赖源文件的程序生成成功。
